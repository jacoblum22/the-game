## What is RPGBench's overall evaluation methodology, and what tasks/scenarios does it use?

### Takeaway
RPGBench evaluates LLMs on two tasks: **Game Creation (GC)** — write a complete, playable RPG-world specification as structured JSON from a Wikipedia character page — and **Game Simulation (GS)** — actually run that JSON game as a multi-round game engine, narrating outcomes and updating state each round. Both tasks are graded by a mix of deterministic/programmatic checks and LLM-as-judge scoring; there is no scenario in the benchmark that is "played" by a human against the model, and no test where the model must recall injected facts without the structured state.

### Cited Findings
- RPGBench "comprises two core tasks: Game Creation (GC) and Game Simulation (GS). In GC, an LLM must craft a valid and playable RPG world using a structured event-state representation... In GS, the LLM simulates interactive gameplay across multiple rounds while consistently updating states and enforcing game rules." — [arXiv:2502.00595](https://arxiv.org/abs/2502.00595)
- Game Creation source data is 100 fictional-character Wikipedia pages (`data/game_creation/characters.jsonl`), and the character becomes the main NPC of the generated game; the HuggingFace mirror confirms exactly 100 rows in the "characters" config, each with `id`, `name`, and a long `description` field (Wikipedia-style text, up to ~94k characters). — [GitHub README](https://github.com/boson-ai/rpgbench-public/blob/main/README.md); [HF dataset page](https://huggingface.co/datasets/DongmingShenDS/RPGBench)
- Games are generated with 5-shot prompting (in-context examples authored with GPT-4o) and must pass a "BFS Validity Checker" before being admitted to the simulation-stage dataset — the checker confirms the generated game graph can actually reach both a success and a failure termination state and that all declared events are reachable. — [arXiv HTML fetch of 2502.00595](https://arxiv.org/html/2502.00595)
- Directly confirmed in code: a valid game JSON has these top-level fields — `game_world`, `player_name`, `player_description`, `main_npc_name`, `main_npc_description` (including a Big-Five personality block with per-trait 1–5 `rate` and free-text `description`, plus an `additional_facts` list of NPC biographical facts), `game_objectives`, `scenes`, `state_variables`, `hidden_variables`, `events`, `pre_event_checks`, `source`. Read directly from `data/games/games.jsonl` on the repo's main branch.
- `state_variables` are player-facing numeric stats (e.g. `creativity`, `friendship`), each with `value_name`, `unique_id`, `description`, `initial_value`, `min_value`, `max_value`. `hidden_variables` are engine-internal flags/counters not shown to the player (e.g. `has_succeeded`, `has_failed`, `tasks_completed`), same schema. — read directly from `data/games/games.jsonl`
- `events` each declare `event_name`, `unique_id`, `scene` (list of scene ids it can occur in), `entering_condition`, `succeed_condition`, `succeed_effect`, `fail_effect`, and a natural-language `explanations` field. Conditions/effects are literal **Python expression strings** (e.g. `"v.creativity > 20"`, `"v.friendship += 10"`, `"h.tasks_completed += 1"`) evaluated at check-time via Python `eval`/`exec` against wrapper objects `v` (state_variables) and `h` (hidden_variables). — read directly from `data/games/games.jsonl` and `rpgbench/evaluation/game_simulation_mechanics.py`
- `pre_event_checks` are global end-of-round rules (e.g. "If Succeeded": condition `h.has_succeeded == 1`, effect `Exit`) checked every round to decide game termination. — read directly from `data/games/games.jsonl`
- In Game Simulation, each round the model follows a fixed **three-stage per-round structure**: (1) Event Planning — decide which declared events fire this round; (2) Game Narration — narrate the outcome and present three candidate next player actions; (3) Game State Update — emit the updated `state_variables`/`hidden_variables` JSON reflecting event effects. — [arXiv HTML fetch of 2502.00595](https://arxiv.org/html/2502.00595)
- Main-experiment simulations run for a fixed 10 rounds per game; a separate ablation extends to {10, 15, 20, 25} rounds. — [arXiv HTML fetch of 2502.00595](https://arxiv.org/html/2502.00595)
- Dataset sizes: 100 Wikipedia character pages → 125 valid generated games total, distributed by generating model as GPT-4o (49), DeepSeek V3 (38), Gemini 2.0 Flash Exp (33), Gemini 1.5 Pro (4), Claude 3.5 Sonnet (1) — [arXiv HTML fetch of 2502.00595](https://arxiv.org/html/2502.00595); HF dataset page independently shows a "games" config with 125 rows, consistent with this. — [HF dataset page](https://huggingface.co/datasets/DongmingShenDS/RPGBench)

### Inferences
- Because every game must pass the BFS reachability checker before being used for simulation, RPGBench's "scenarios" are synthetic, LLM-authored, and mechanically pre-validated — not hand-authored adventure modules and not real human playtests. This matters for anyone adapting the approach: the benchmark's ground truth ("is state correct?") comes entirely from replaying the declared JSON rules against the model's own turn-by-turn output, not from an external oracle.
- The Python-`eval`/`exec` condition/effect language is a deliberate design choice that makes objective grading purely mechanical (re-run the same interpreter used to author the game against the model's claimed round-state), which is exactly the "externalize state, verify with code, not vibes" idea our own tool-calling architecture should be benchmarked against.

### Gaps
- The exact wording/rubric given to the *simulating* model each round (the system prompt/tool schema it's asked to emit) was not directly retrievable in this pass — the repo's `scripts/game_simulation/` directory exists but its file contents (the actual prompt templates) were not fetched due to tool-budget constraints. The `rpgbench/static/` directory (referenced by `game_simulation_factuality.py` as holding prompt `.txt` files) likewise was not opened. Recommend a follow-up fetch of `rpgbench/static/*.txt` and `scripts/game_simulation/*.py` if exact prompt wording is needed.

## Does RPGBench test state-tracking/memory specifically? What does a test case look like?

### Takeaway
Yes — state-tracking is the central, most heavily instrumented part of Game Simulation. A test case is a synthetic, pre-validated JSON game (numeric state variables + hidden flags + conditional events with Python-expression conditions/effects) that the model plays turn-by-turn; after each round the harness deterministically replays the game's own declared rules against the model's previous state and checks whether the model's newly-emitted state matches what the rules dictate. It is not a set of "injected facts to recall later" in the narrative sense — it's closer to a compiler re-executing a program and diffing the interpreter's state against the model's self-reported state.

### Cited Findings
- The check is implemented in `GameChecker.validate_game_per_round` (`rpgbench/evaluation/game_simulation_mechanics.py`): for every round it (1) runs global `pre_event_checks` to see if the game should have ended; (2) for each planned event of type `Start`, verifies the model didn't fire an event whose `entering_condition` wasn't actually true in the *previous* state; (3) for `End`/`Success` events, verifies `succeed_condition` was true before applying `succeed_effect`; (4) for `End`/`Fail` events, verifies `succeed_condition` was actually false before applying `fail_effect`; (5) after mechanically re-applying the correct effects to the previous state, it diffs that recomputed "should-be" state against the state the model actually output for the round, per-variable. — read directly from source
- Per-variable diff has three buckets, all computed automatically: `state_var_update_error_complete_mismatch` (model's new value doesn't match the previous value *or* the correctly-recomputed value — i.e. it just diverged), `state_var_update_error_range_invalid` (model's value equals the old value — i.e., failed to update at all — but the correct value differs only because of a min/max clamp), and no-error (exact match). Hidden variables get the identical treatment. — read directly from `game_simulation_mechanics.py`, `check_state_update`
- Formal per-round error score: `event_condition = event_condition_check_error / max(1, num_events)`; `var_update = (state_var_update_error_complete_mismatch + hidden_var_update_error_complete_mismatch) / (num_hidden_vars + num_state_vars)`; a "strict" variant additionally counts the range-invalid errors. Overall trajectory score is the mean per-round score across all valid rounds, plus `final_error_free_rounds` = fraction of rounds with **zero** mechanical error. — read directly from `process_errors` in `game_simulation_mechanics.py`
- Separately, **factual/narrative consistency** (as opposed to mechanical/numeric state) is tested by giving an LLM judge the NPC's `additional_facts` list (extracted from the source Wikipedia description at game-creation time) plus the *full narrated transcript* the simulating model produced, and asking the judge to classify, per fact, whether the playthrough's narration `align`s with, `contradict`s, or is `neutral` toward each fact. — read directly from `rpgbench/evaluation/game_simulation_factuality.py`
- The factuality check's `align_ratio` / `contradict_ratio` / `informative_ratio` / `align_relative` are all computed as simple counts over the judged fact list (`align / total`, etc.) — read directly from `compute_fact_scores` in the same file.
- Personality consistency (PER) is tested with a psychometric instrument: the transcript is scored against the Ten-Item Personality Inventory (TIPI), converted to Big-Five trait scores, and compared via normalized Euclidean distance to the personality trait ratings baked into the game JSON's `big5_personality_traits` block at creation time. — [arXiv HTML fetch of 2502.00595](https://arxiv.org/html/2502.00595); the game JSON schema for `big5_personality_traits` (per-trait `rate` 1–5 and `description`) was directly confirmed in `data/games/games.jsonl`.

### Inferences
- RPGBench's state-tracking test is fundamentally about **numeric/logical game-state consistency under an explicit machine-checkable rule set**, not about long-range recall of arbitrary narrative facts planted early in a conversation. The "memory" being tested is: does the LLM correctly carry forward and update a small structured JSON object it re-emits every turn, and does it only trigger events whose preconditions are actually true given that object's current values. This is architecturally close to what a tool-calling D&D engine would need, except RPGBench has the *model itself* produce the JSON state text each round (no external tool call/write) — the JSON is graded after the fact by replaying rules against the *narrative transcript*, not enforced during play by a real state-writing tool.
- Because grading works by re-running the same event graph that generated the game, this methodology is directly transferable to a tool-calling D&D stress test: author a small, validated state machine (numeric stats + hidden flags + conditional "events"/checks with real preconditions and effects) and diff the model's declared tool-call arguments against ground truth recomputed by the same rule interpreter, exactly as RPGBench's `GameChecker` does.

### Gaps
- No test case in RPGBench appears to inject "facts to recall 50 turns later" as an explicit adversarial probe (e.g., "the door was locked in turn 3, does the model remember at turn 40"); the design instead relies on emergent drift over a fixed 10–25 round horizon, measured statistically rather than via planted single-fact recall probes. If our own benchmark wants that recall-probe style, it would be a genuine methodological addition beyond what RPGBench does.

## Findings on which models/architectures are better or worse at maintaining consistent game state, and why

### Takeaway
Gemini 2.0 Flash Exp had the best mechanical-consistency score (MEC) in Game Simulation despite Gemini 1.5 Pro being by far the worst at Game Creation validity; GPT-4o was strong at Game Creation but mid-pack on mechanical consistency during simulation; and consistency (MEC) reliably **degrades as trajectory length increases** for the model tested longitudinally (GPT-4o), which the paper attributes to accumulating context/state complexity rather than any single architectural cause. The paper's own explanation is fairly high-level: it does not isolate parameter count, context window, or training method as the driver — it primarily reports the correlation between round count and degradation and to a companion decline in narrative interestingness (repetition).

### Cited Findings
- Game Creation validity (Table 2, per the arXiv HTML fetch): GPT-4o VCR 0.49 (highest), DeepSeek V3 VCR 0.38, Gemini 2.0 Flash Exp VCR 0.33, Gemini 1.5 Pro VCR 0.04 (lowest); Claude 3.5 Sonnet had a ~95% refusal rate on the Game Creation task itself (largely opting out rather than producing invalid games). — [arXiv HTML fetch of 2502.00595](https://arxiv.org/html/2502.00595)
- Game Simulation mechanical scores at 10 rounds (Table 3, per the arXiv HTML fetch): Gemini 2.0 Flash Exp MEC 0.765 (best), GPT-4o MEC 0.693, Gemini 1.5 Pro MEC 0.554; factual consistency (FAC) ranged 0.885–0.991 across models tested, and interestingness (INT) ranged 0.420–0.722. — [arXiv HTML fetch of 2502.00595](https://arxiv.org/html/2502.00595)
- Trajectory-length ablation on GPT-4o across {10, 15, 20, 25} rounds: FAC increases then stabilizes with length, INT decreases (attributed to repetitive narration), and MEC declines as the trajectory gets longer — i.e. mechanical/state-tracking accuracy is the metric most damaged by extending the horizon. — [arXiv HTML fetch of 2502.00595](https://arxiv.org/html/2502.00595)
- The paper's overall qualitative conclusion: state-of-the-art LLMs "can produce engaging stories but often struggle to implement consistent, verifiable game mechanics, particularly in long complex scenarios." — [arXiv:2502.00595 abstract](https://arxiv.org/abs/2502.00595)
- Human-vs-LLM-judge correlation on a 20-game subset was weak: Pearson r ≈ 0.129 for factual consistency judgments and ≈ 0.140 for interestingness judgments, flagged by the paper itself as evidence the subjective metrics (as opposed to the deterministic mechanical checks) are noisy/unstable. — [arXiv HTML fetch of 2502.00595](https://arxiv.org/html/2502.00595)

### Inferences
- The dissociation between Game-Creation validity (which model can *author* a coherent rule-following game) and Game-Simulation mechanical consistency (which model can *follow* a rule-following game someone else wrote) is itself informative: Gemini 1.5 Pro was almost unable to author valid games (VCR 0.04) yet was still evaluated in simulation with a respectable MEC of 0.554 — meaning "can generate a correct constrained JSON world" and "can maintain consistent state while playing one" are different skills that don't fully transfer, which is relevant if our own stress test conflates "can the model design an encounter" with "can the model track HP/inventory/position through many turns."
- The reported length-ablation (MEC declining with rounds, run only for GPT-4o) is the paper's single clearest piece of evidence for exactly the failure mode our own long-horizon consistency test cares about, but it's a within-model ablation on one model family, not a cross-model comparison at long horizons — the cross-model Table 3 numbers above are all at the fixed 10-round setting.

### Gaps
- The paper does not appear to offer a mechanistic explanation (e.g., attention dilution, training-data distribution, RLHF effects) for *why* MEC declines with length — it reports the correlation/trend without a causal account. It also does not run the {10,15,20,25}-round ablation for the other models (Gemini, DeepSeek), so it's unconfirmed whether the degradation-with-length pattern generalizes across architectures or is GPT-4o-specific. Flagging this as an open question rather than guessing.

## Does RPGBench have findings on state representation format (structured JSON/tool-based vs. natural-language tracking) affecting reliability?

### Takeaway
RPGBench does not run a controlled ablation comparing "model tracks state in JSON" vs. "model tracks state purely in freeform narrative memory" — every model in the benchmark is required to emit the same structured JSON state block every round, so the benchmark's design itself is a de facto argument for structured state (it's the only way they make objective, human-judgment-free grading possible), but this is an architectural choice baked into the benchmark, not an experimental finding comparing formats head-to-head.

### Cited Findings
- The paper states the structured event-state representation is what "enables automated, robust assessments of mechanical correctness" without requiring human judgment, explicitly contrasting this against subjective, judgment-dependent evaluation. — [arXiv HTML fetch of 2502.00595](https://arxiv.org/html/2502.00595)
- Confirmed directly in code: the *simulating* model is the one producing the state JSON text each round (via `parse_game_output(trajectory[round_id]['content'])`), which the harness then parses and diffs against the mechanically-recomputed ground truth — there is no real external tool call that writes state on the model's behalf in RPGBench's setup; the model narrates a text turn that embeds both the narration and a JSON `event_plan`/state block, and the harness's own Python interpreter (not the LLM) is the source of truth for what state *should* be. — read directly from `game_simulation_mechanics.py`

### Inferences
- Because RPGBench never asks a model to track state purely in free-form prose (all models are constrained to emit the same JSON schema every round), it cannot speak to whether JSON-structured output is more reliable than narrative-only tracking — that comparison, which is central to our own research question, is simply outside RPGBench's design space. What RPGBench *does* establish is the complementary point: even when every model is required to emit structured state, and even though that structure is what makes objective grading possible at all, models still generate mechanically invalid state updates at meaningful rates (MEC of 0.55–0.77 at only 10 rounds, declining further with length) — i.e., structured output format alone does not guarantee correctness; the model must also correctly *compute* what the structure should contain. This is a directly useful cautionary data point for a tool-calling architecture: routing state through a real tool call (as our design does) moves the "did state update correctly" check from post-hoc textual parsing (RPGBench's approach) to an enforced call the model must construct correctly, but RPGBench's numbers suggest LLMs still make outright arithmetic/logical errors in exactly this kind of update even when the shape of the output is fixed and enforced by the harness's parser.

### Gaps
- No source found (paper, repo, or otherwise) that runs RPGBench or an RPGBench-style task under two conditions — structured/JSON-enforced state vs. purely narrative state tracked in context — and compares consistency outcomes. This is a genuine gap in the literature as far as this research pass could determine, and appears to be exactly the kind of ablation our own benchmark would need to originate rather than borrow.

## What metrics does RPGBench report, precisely, and what were the actual quantified results for leading models?

### Takeaway
RPGBench reports two Game-Creation metrics (FCR, VCR) and five Game-Simulation metrics (MEC/mechanics, FAC/factual consistency, PER/personality consistency, INT/interestingness, ACT/action-choice quality), all defined by concrete formulas or judge rubrics found in the repo's evaluation code; Table 2 and Table 3 of the paper give per-model numbers, with the highest Game-Simulation mechanical score being Gemini 2.0 Flash Exp at MEC 0.765 (10 rounds) and the highest Game-Creation validity being GPT-4o at VCR 0.49.

### Cited Findings
- **Format-Check Pass Rate (FCR)** and **Validity-Check Pass Rate (VCR)** for Game Creation: FCR checks the output is well-formed JSON matching the schema; VCR additionally requires the BFS validity checker to confirm the game graph is playable (reachable success and failure states, all events reachable). — [arXiv HTML fetch of 2502.00595](https://arxiv.org/html/2502.00595); checker logic partially confirmed in `rpgbench/evaluation/game_creation_validity.py` (288 lines, contains the reachability/BFS logic — not fully read in this pass, see Gaps).
- **Mechanics (MEC)**: defined in code as `final_error_free_rounds` — the fraction of simulated rounds with zero mechanical error across event-condition checks and variable-update checks (see previous section for the exact per-round formula). — read directly from `game_simulation_mechanics.py`
- **Factual Consistency (FAC)**: LLM judge classifies each of the NPC's pre-declared `additional_facts` as align/contradict/neutral against the played transcript; score = `align / (align + contradict)` (the code's `align_relative` field). — read directly from `game_simulation_factuality.py`
- **Personality Consistency (PER)**: TIPI-derived Big-Five score from the transcript, compared via normalized Euclidean distance to the game's declared `big5_personality_traits`. — [arXiv HTML fetch of 2502.00595](https://arxiv.org/html/2502.00595); confirmed a dedicated `game_simulation_personality.py` (107 lines) implements this — not fully read in this pass.
- **Interestingness (INT)**: LLM judge rates narrative engagement 1–5, normalized to [0,1]. — [arXiv HTML fetch of 2502.00595](https://arxiv.org/html/2502.00595); confirmed a dedicated `game_simulation_interestingness.py` (short, 1398 bytes) exists in the repo.
- **Action Choice Quality (ACT)**: three sub-rubrics per round — Diversity ("offer distinct and varied options"), Relevance ("contextually aligned"), Understandability ("clear, concise") — each scored 1–5 by an LLM judge and averaged/normalized. — [arXiv HTML fetch of 2502.00595](https://arxiv.org/html/2502.00595); confirmed a dedicated `game_simulation_action.py` (146 lines) exists.
- Quantified headline numbers: Game Creation — GPT-4o VCR 0.49, DeepSeek V3 VCR 0.38, Gemini 2.0 Flash Exp VCR 0.33, Gemini 1.5 Pro VCR 0.04, Claude 3.5 Sonnet ~95% refusal rate. Game Simulation at 10 rounds — Gemini 2.0 Flash Exp MEC 0.765, GPT-4o MEC 0.693, Gemini 1.5 Pro MEC 0.554; FAC 0.885–0.991 across models; INT 0.420–0.722 across models. — [arXiv HTML fetch of 2502.00595](https://arxiv.org/html/2502.00595)
- Human-judge correlation check on a 20-game subset: Pearson r ≈ 0.129 (FAC) and ≈ 0.140 (INT) between human and LLM-judge scores. — [arXiv HTML fetch of 2502.00595](https://arxiv.org/html/2502.00595)

### Inferences
- The weak human/LLM-judge correlation on the *subjective* metrics (FAC as judged, INT) versus the fully deterministic MEC metric (computed by literally re-executing the game's own rule interpreter, no LLM judge involved) suggests MEC is the most trustworthy number in the paper, and is also the metric most analogous to what a real tool-calling architecture could enforce/measure directly (as opposed to FAC/INT/PER/ACT, which rely on a second LLM's subjective read of a transcript).

### Gaps
- Because the OpenReview PDF could not be fetched (bot-blocked) and the arXiv PDF itself was not separately parsed (only the arXiv HTML rendering, via a summarizing WebFetch call, was used), the exact table numbers above are second-hand through one AI summarization pass rather than a direct read of the table's raw text/LaTeX. They should be treated as "reported, plausible, likely accurate" rather than hand-verified byte-for-byte. If exact precision matters for citation, recommend re-fetching `https://arxiv.org/pdf/2502.00595` directly (rather than the HTML mirror) or downloading and parsing the PDF locally.
- Format-Check Pass Rate (FCR) numbers per model were not captured in this pass (only VCR was reported by the summarizer) — a gap if the full FCR table is needed.

## Does RPGBench publish its dataset construction / prompts concretely enough to adapt from?

### Takeaway
Yes, substantially — the GitHub repo is a working implementation, not just a paper artifact: it contains the actual game-JSON schema, the actual generated games (125 of them, directly inspectable), the actual evaluation/grading source code for every metric, and (per file names not yet opened) prompt templates under `rpgbench/static/`. This is concrete enough to adapt the JSON schema, the condition/effect mini-language, and the per-round grading algorithm directly.

### Cited Findings
- Repo top-level layout: `data/` (game_creation source characters, generated games, game_creation_evaluation, game_creation_generation, game_simulation_generation trajectories, games, evaluation_debug), `rpgbench/` (the Python package: `evaluation/`, `game/`, `models/`, `static/`, `utils/`), `scripts/` (`game_creation/`, `game_simulation/` — generation and evaluation entry-point scripts), plus `conda_env.yml`, `LICENSE`, `README.md`. — enumerated directly via GitHub API
- `rpgbench/evaluation/` contains one file per metric: `game_creation_validity.py` (288 lines), `game_simulation_action.py` (146 lines), `game_simulation_factuality.py` (55 lines, fully read above), `game_simulation_interestingness.py`, `game_simulation_length.py`, `game_simulation_mechanics.py` (321 lines, fully read above), `game_simulation_personality.py` (107 lines), plus a shared `evaluation_utils.py`. — enumerated and partially read directly
- The actual generated-game dataset (`data/games/games.jsonl`, 125 lines, ~1MB) was downloaded and parsed directly in this research pass; a full example entry (the "Mickey Mouse" game) was inspected field-by-field, confirming the schema described above is real and not just a paper description.
- A mirrored copy is hosted on Hugging Face at `DongmingShenDS/RPGBench` with two configs — "characters" (100 rows: `id`, `name`, `description`) and "games" (125 rows) — confirming the same 100→125 pipeline described in the paper. — [HF dataset page](https://huggingface.co/datasets/DongmingShenDS/RPGBench)
- README explicitly directs users to run `scripts/game_creation/` generation/evaluation scripts and `scripts/game_simulation/` generation/evaluation scripts locally, with conda-based environment setup, and supports both API-based models and local model deployment (OpenAI-compatible API or Ray cluster). — [GitHub README](https://github.com/boson-ai/rpgbench-public/blob/main/README.md)

### Inferences
- Given the repo is a complete working harness (schema + generator prompts + grading code + example outputs), the most direct adaptation path for our own D&D tool-calling benchmark is: (1) borrow the numeric-state + hidden-flag + conditional-event-with-Python-expression schema wholesale or as a close analog for our own JSON state, (2) borrow the "replay the same rule interpreter against the model's claimed state, diff per-variable" grading algorithm from `GameChecker.validate_game_per_round`/`check_state_update`, since it's genuinely tool-agnostic and would work equally well auditing real tool-call arguments instead of parsed narrative-embedded JSON, and (3) treat their subjective LLM-judge metrics (FAC/INT/PER/ACT) as optional color commentary rather than trustworthy scores, given the reported human-correlation was weak.

### Gaps
- `rpgbench/static/` (which holds the prompt templates, e.g. `game_character_facts_prompt.txt`, `game_character_facts_json_schema.json`, `game_character_facts_example.json` referenced by `game_simulation_factuality.py`) and `scripts/game_simulation/*.py` (the actual per-round simulation driver and its system prompt to the model-under-test) were located but not opened in this research pass due to tool-call budget — recommend a targeted follow-up read of those specific files if exact prompt wording is required for direct adaptation.
- `game_creation_validity.py`'s BFS reachability algorithm (288 lines) and `game_simulation_action.py`/`game_simulation_personality.py`'s exact judge-prompt wording were not read line-by-line in this pass; only their existence, purpose, and (for action) the three sub-rubric names/definitions were confirmed via the arXiv summary.
